# Details: 0009. Cutover soak window and fallback threshold

## Context

OPS-1 flips `NUXT_PUBLIC_CONFIG_SOURCE=registry` one deployment at a time, dev then stg then prod,
soaking between flips, and its pass/fail gates p04-01. The window and the threshold are authored
here deliberately: a verification gate must not set the bar it is judged against.

p02-09 emits `config.source.fallback` as a single structured line per event, carrying `siteCode`,
`env`, `multiSiteCode`, `servedFrom`, a timestamp, and a `reason` from a fixed enum:
`registry-unreachable`, `registry-row-malformed`, `site-absent-from-registry`,
`drupal-unreachable`, `last-known-good-served`. It also keeps a per-container counter keyed on
`env:multiSiteCode:siteCode:reason`, exposed on an authenticated diagnostics route.

**The counter has no denominator.** It counts fallbacks, never total config reads, and the
per-container copy resets on restart. A "fallback rate" expressed as a percentage is therefore not
answerable by the instrument OPS-1 actually has — only an absolute count over a window is.

## Considered options

1. **Absolute count per window, per reason (Recommended).** Query the log aggregator for
   `config.source.fallback` over the window, grouped by `reason`, filtered to the flipped `env`.
   Pass when `site-absent-from-registry` is zero and `registry-unreachable` is at most one.
   Directly answerable today; a single blip does not fail a 72-hour prod soak, but a pattern does.
2. **Zero tolerance on every reason.** Simplest to state and strictly safest. Cost: one transient
   network error restarts a 72-hour prod soak, which pressures the operator into relaxing the bar
   mid-run — exactly the failure mode this ADR exists to prevent.
3. **Percentage rate against total reads.** The instinctive shape, but it requires p02-09 to also
   emit a total-config-read counter, which it does not. Choosing this means amending p02-09 first;
   OPS-1 cannot run until that lands.

## Proposed windows

| Slice | Window | Reasoning |
|---|---|---|
| dev | 24 hours | One full traffic cycle, cheap to repeat. |
| stg | 48 hours | Two cycles, including a weekday/weekend boundary where possible. |
| prod | 72 hours | Long enough to cross a container recycle and a scheduled re-seed (p02-06). |

## The query

Group `config.source.fallback` records by `reason` over the window, filtered to the flipped `env`,
and compare against the counts above. Baseline the counter before the flip and measure the delta,
not the lifetime total. The per-container diagnostics route is a secondary signal only, because it
resets on restart.
