# Details: 0008. Registry backup posture

## Context

`server/assets/schema.sql` creates and uses a database named `i18n_cache`, and the runtime default
matches. Everything in that database today is regenerable: a truncated translation cache costs an
AWS Translate bill and some latency. Plan decision 1b puts the registry tables there to avoid new
credentials.

That makes the registry the first non-regenerable data in a database whose name says it is
disposable. Losing it is a 404 on every page (see ADR 0006).

## Considered options

1. **A separate database, same server (Recommended).** A `site_registry` database beside
   `i18n_cache`, so the name carries the meaning and a truncate aimed at translations cannot reach
   config. `I18N_DB_NAME` (`nuxt.config.ts:63`, `server/utils/translate/index.js:37`) selects only
   the pool's default schema; cross-database qualified names (`site_registry.sites`) run on that
   same pool under the same credentials. Cost: one grant, no new variables — decision 1b's "zero
   new configuration" property survives intact.
2. **Same database, documented non-truncatable and backed up.** Tables stay in `i18n_cache`. The
   schema file carries a `COMMENT` on each registry table saying it is durable config and must not
   be truncated; the backup covers it; p02-02's seeder is the verified rebuild path. Cost: the
   protection is a convention plus a backup, not a structural boundary — a broad
   `DROP DATABASE i18n_cache` still takes both.
3. **Same database, accepted as risk, debt row only.** No backup change, no rename; p04-04 records
   the exposure and the rebuild. Cost: recovery depends on the dmsm JSON5 files still existing,
   untrue once the decommissioning plan runs.

## Recovery path

Under every option the rebuild is p02-02's seeder: `--env` and `--multi-site-code` are mandatory,
the upsert is keyed on `(env, multi_site_code, site_code)`, and a re-run converges to identical
rows. One slice is 211 bl2 sites or 11 bsl sites, so a reseed is minutes — but only as current as
the dmsm JSON5 source, which p02-06's drift check exists to catch. Last-known-good `biolandSettings` (D-C) and
p02-07's network summary are **not** in the JSON5 files; they repopulate on the next successful
read and push.

## Consequences

Option 3 requires a p04-04 debt row naming the truncation exposure and the rebuild procedure.
Options 1 and 2 change p02-01's schema destination or its column comments.

Option 1 is recommended on the corrected cost: one grant buys a structural boundary, dominating
option 2's convention-plus-backup at the same configuration price. p02-01 writes
qualified table names and the schema file creates the second database.
