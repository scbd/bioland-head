# Details: 0006. Degraded-mode policy when site config is unavailable

## Context

`resolveSiteContext` fetches config, and a `null` result throws a 404 with
`Site configuration not found for: ${siteCode}` — the plan cites this as
`server/utils/context-unified.ts:75-81`; on this branch the block sits at `:110-116`. The throw is
unconditional and pre-render, so it takes every route of that site, not one page.

Today a registry failure would fall back to dmsm (p03-02). p04-01 deletes that fallback, at which
point "registry unreachable" and "site absent from the registry" both land on the same 404. The
two failures are not the same: an absent site is a correct answer, an unreachable registry is not.

## Considered options

1. **Fail closed — keep today's 404.** An anonymous visitor gets a bare 404 on every URL of every
   site in the deployment for the whole outage. Cheapest: p03-02 and p04-01 change nothing, and no
   new state is introduced. Cost: a DB blip becomes a full public outage with no partial service.
2. **Serve last-known-good from a stale-tolerant cache (Recommended).** The config path already has
   a 5-minute `cachedFunction` FS cache (`context-unified.ts:183`, `CACHE_TTL.FIVE_MINUTES`, storage
   base `./cache`). Extend it to serve a stale entry when the read fails, emit p02-09's
   `config.source.fallback` with a `last-known-good-served` reason, and degrade anything the stale
   payload cannot carry. A visitor sees the site, possibly with a stale theme or locale list. Cost:
   p03-02 gains a stale-serve branch and a retention decision; a cold container that never cached
   the site still 404s.
3. **Serve a static minimal shell per site.** A build-time per-site fallback document renders a
   branded holding page. Cost: a new artifact, a new build step, and a second config shape to keep
   in sync — the most code for the least reuse.

## Decision drivers

- Blast radius: the 404 is per-deployment and total, not per-page.
- `null` must stay a real answer for a genuinely absent site (p03-02 step 7 forbids masking a
  seeding gap), so whatever we choose must distinguish unreachable from absent.
- ADR 0005 is **not** cited here: `GET_LOCK` has zero code hits in this repo, so 0005 is
  aspirational and is no precedent for anything.

## Consequences

p03-02 implements the chosen policy on the registry branch; p04-01 preserves it when the dmsm
branch is deleted. If option 1 is chosen, p04-04 should carry a debt row naming the dark-deployment
risk.
