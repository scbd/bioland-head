# 0010 details

## The shared-mount finding

`nuxt.config.ts:21,254` bind the `cache` storage base to `./cache` in production. Whether that
path is per-container or one shared volume decides the whole design, and the repo cannot answer
it: `Dockerfile:73` only creates the directory.

The deployment answers it. **`./cache` is a shared mount** across the fleet. Source: the user,
2026-09-15, as a direct verdict on this question. ADR 0005 asserts the same thing, but 0005 does
not exist in `docs/adr/` (the directory holds 0001, 0002, 0010 and 0012) and its `GET_LOCK`
pattern has zero code hits, so it is not cited here as precedent.

## Decision drivers

- Config is read on essentially every request. Anything added to that path is paid millions of
  times a day.
- A publish is rare. Work belongs on the write side.
- The fleet has no container discovery and no message bus, so a broadcast would need one built.

## Considered options

| Option | Why not |
|---|---|
| **Chosen: delete from the shared store** | Write-side only, no new infrastructure, zero read cost, bound of zero. |
| Monotonic generation per site, compared on read | Buys nothing here. Every container already sees the deletion, so the comparison can only ever agree. Its cost is a registry read on the config path, amortized at best to one per site per N seconds per container, and not amortized at all on the uncached caller. |
| Broadcast to peers | Needs container discovery, and a container that was down during the publish stays stale. |

## Consequences

- p02-01 creates a generation column that **nothing reads or writes**. It is left in place and
  unused rather than given an invented consumer. Dropping the column is p04's call.
- The design depends on the mount staying shared. If a future deployment gives each container its
  own volume, invalidation silently degrades to per-container and this ADR must be superseded,
  not patched. Nothing in the code can detect that change.
- `clearSiteCache` (`server/utils/nitro-cache.js:24`) is untouched and keeps working. This adds a
  narrower, named entry point beside it; it replaces nothing.

## Staleness bound

**0 seconds.** There is no read-side check to amortize, so there is no window to bound. Two
residuals sit outside it and cannot be closed by any mechanism on this seam:

1. A request already past its own cache read finishes on the value it loaded.
2. The shared volume's own metadata visibility latency. Zero on a POSIX bind mount; a network
   volume with client attribute caching adds its attribute-cache TTL.

## Per-request cost, and the bypass path

Zero, everywhere. `fetchDmsmConfigCore` has two callers: the cached path
(`context-unified.ts:145`) and the `bypassCache` path (`:167`). The bypass path is uncached by
design and refetches every time, so it cannot serve a stale config and needs no check. Had the
generation counter shipped, `:167` would have carried a per-request registry read with none of
the cached path's amortization, which is the second reason it was dropped.

## The `completed:` marker

`server/middleware/00.cache-clear.ts:59-62` writes a `completed:{value}` marker with a 60s TTL
and returns early while it is present. If that marker ever lives in a shared store, the first
container to finish suppresses the clear fleet-wide for the next 60s.

`invalidateSiteConfig()` never reads the `cache-clear` base, so that early return cannot gate it.
A test asserts this by seeding a fresh marker and showing the entries still go
(`tests/unit/server/utils/site-registry/invalidation.test.ts`).

## Failure behaviour

An unreachable or failing store is logged and swallowed. A publish must not crash because a cache
volume hiccuped, and entries that survived expire on their own TTL. An empty argument throws
instead, because a missing site code matches nothing and would otherwise report a fleet-wide
no-op as a success.
