# Details: 0007. Per-environment config database topology

## Context

Every connection value is an environment variable resolved at runtime
(`nuxt.config.ts:57-66` → `server/utils/translate/index.js:33-40`). Nothing in this repo records
which server a given deployment's variables point at, so the topology is an operator fact, not a
code fact. This ADR names the variables only; no host, credential, or connection string appears in
this repo.

Plan decision 6 scopes the registry to one `env` x `multiSiteCode` deployment and claims that as
the tightest blast radius. That claim holds only if the environments do not share one server.

## Considered options

1. **Distinct server per environment (Recommended).** p02-01 keeps `env` and `multi_site_code`
   columns for seeder idempotency, but a mistake can only ever reach one environment's data.
   p02-02's seeder runs per slice against its own server, and a prod flip cannot be corrupted by a
   dev re-seed. Cost: nothing new — this is the shape p02-01 is already drafted against.
2. **One shared server, isolated by the `env` column.** p02-01's `env` column stops being defensive
   and becomes load-bearing: every read needs a hard per-environment filter, and a missing `WHERE
   env = ?` silently serves prod a dev row. p02-02 must also refuse to run without `--env`, which
   it already does. Cost: the isolation becomes a code invariant enforced by tests rather than by
   infrastructure, and one truncation takes all three environments.
3. **Distinct server, plus a separate `CONFIG_DB_*` variable set.** Strongest isolation — config
   reads stop sharing the translation pool entirely. Cost: new operator-supplied variables, new
   credentials to provision, and it drops plan decision 1b's "zero new infrastructure" property.

## Decision drivers

- p02-01 step 3 already keeps `env` columns "as the only defense if a DB is ever shared", so both
  answers are implementable; the answer sets how hard the read filter must be tested.
- Option 3 interacts with pool contention (C13): config reads currently inherit the shared
  `acquireTimeout: 30000` from `createPool`.

## Consequences and manual action

If option 3 is ruled, a new `CONFIG_DB_HOST` / `_PORT` / `_USER` / `_PASSWORD` / `_NAME` /
`_CONNECTION_LIMIT` set must be added by hand to each deployment environment. The values are
operator-supplied. No task in this plan writes a `.env*` path (Plan Rule 26).

Independently of the ruling, `I18N_DB_CONNECTION_LIMIT` must be raised above its default of 5
before the first flip, since config reads join the translation workload on one pool.
