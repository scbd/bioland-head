# 0002. Details

## Considered options

- **Reject or allowlist `x-forwarded-host` at the app layer**, honoring it only from a known proxy
  address. Correct defense in depth, but rejected for this plan: it changes existing behavior for
  every Site and environment, needs a proxy-address contract per deployment, and widens a plan
  scoped to the redirect Host. Recorded as a follow-up, not a task here.
- **Drop `x-forwarded-host`, trust `host` only.** Rejected: it breaks the deployment model, where
  the edge forwards the original host in `x-forwarded-host` and the origin never sees it in `host`.

## Decision

The plan does not change bioland-head's in-app trust model. No allowlist, no header rejection. Two
things change instead. The 301 target is always the Site's canonical Host read from DMSM config,
never derived from a request header, so the redirect itself cannot become an open redirect. The
edge trust boundary becomes a hard rollout prerequisite gating deployment of the flip task
(`p03-01`), not a code change in this plan: the edge (Traefik) must overwrite any client-supplied
`x-forwarded-host` with the real host, the origin must be reachable only through that proxy, and a
negative test must show a client-supplied header cannot change the resolved Site.

## Consequences

- The security posture of `x-forwarded-host` trust is unchanged by this plan. It was already the
  app's behavior before the redirect-Host feature existed.
- No Site may enable its `redirect` config until the edge boundary is verified, so the rollout gate
  carries real weight, not a formality.
- The residual risk, an app-level trusted-proxy allowlist, is not eliminated. It is recorded as a
  follow-up outside this plan and stays open until someone files and ships it.
- If the edge boundary is ever misconfigured or removed, the exposure returns. Nothing in this
  plan's code catches that; only the rollout gate's negative test and later infrastructure review
  would.

## Review evidence

Devil's-advocate review verdict, 2026-09-10: 2 cross-model critics, 3 rounds. Objection O7 (round
1, both critics, accepted: pre-existing trust, not widened by this plan, rollout verification
added) was reopened as O28 (round 3, one critic), accepted for code scope and resolved as the
rollout gate above rather than an in-app code change. No high-impact objection survived past
round 3.
